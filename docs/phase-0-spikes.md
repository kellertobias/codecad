# Phase 0 spike verdicts

Findings behind the decisions in [the roadmap](full-cad-roadmap.md) (D2–D4,
D6), each backed by code or tests in this repository. Measured on an Apple
Silicon Mac, Node 25, Chromium, 2026-09-26.

## Kernel in a browser worker (D2): works

`web/kernel/worker.ts` runs the existing `OpenCascadeEngine` in a module Web
Worker and returns meshes as transferable typed arrays. `/kernel-probe`
reports timings:

| Step                                                   | Time            |
| ------------------------------------------------------ | --------------- |
| Kernel ready after page start (localhost)              | 76 ms           |
| WASM download, compile and init inside the worker      | 48 ms           |
| 100 × 50 × 20 box: build / mesh                        | 4 ms / 32 ms    |
| 600 × 300 × 18 panel with 16 bored holes: build / mesh | 477 ms / 351 ms |

- **How it works:** the engine and the rest of the CAD core already ran
  unchanged in the browser. The only obstacle was `brepjs/quick`, which finds
  its kernel through a computed dynamic import. Browser bundles alias it to
  `src/kernel/browser-brepjs.ts`, which loads the served WASM explicitly
  (`scripts/web-bundles.mjs`).
- **STEP files:** the engine read STEP files through `node:fs`. That is now a
  reader that can be swapped, and the worker fetches the files instead.
- **Mesh buffers:** `brepjs` mesh arrays own their buffers; they are not views
  into WASM memory. Transferring them is therefore safe.
- **Guard:** `tests/isomorphic-core.test.ts` fails if any core module imports a
  Node built-in.
- **Cost:** the WASM is 22 MB, or 7 MB gzipped. On localhost it loads in tens
  of milliseconds. Over a network, the download dominates. The server serves
  the WASM with a one-day cache but does not compress yet. Add gzip or brotli,
  or precompressed files, before remote use.
- **Performance to watch:** chains of booleans cost hundreds of milliseconds,
  because 16 sequential cuts rebuild the solid 16 times. Two things are needed
  to hit the roadmap's 300 ms regeneration budget:
  - per-feature caching, so an edit only replays from the feature that changed
  - batching repeated tools into one compound cut (a planned optimisation for
    patterns).

  Tessellation at the current fine tolerance is the other large cost. A coarser
  preview mesh while dragging is an easy win.

- **Memory:** Chromium does not report memory inside a worker
  (`performance.memory` is main-thread only). The kernel heap is not measured
  yet. `measureUserAgentSpecificMemory` needs cross-origin isolation, which
  can be added once the server sends COOP/COEP headers.

## Stable face references (D4): works, with our own extrude naming

`tests/stable-references.test.ts` builds a plate: an extrude, then a pocket cut
into its top, then a rounded corner. It then rebuilds the plate with different
width, depth, height and pocket position, and adds a notch that changes the
sketch's edge count. References captured on the first build resolve on the
second:

| Reference                            | Result after the rebuild                                |
| ------------------------------------ | ------------------------------------------------------- |
| A wall, `side:left`                  | exact match                                             |
| The top face, pierced by the pocket  | resolved                                                |
| The pocket floor                     | found at its new depth and position                     |
| The fillet round                     | found through `brepjs` derived-face refs                |
| A wall whose sketch edge was deleted | no exact match, so the evaluator must ask for a re-pick |

- **Naming:** `brepjs` names primitive faces semantically (`box:top`), but names
  every other face positionally (`extrude:face_3`). Positional names shift when
  a sketch changes, so `src/kernel/roles.ts` names extrude faces itself:
  - `start` and `end` for the caps
  - `side:<sketch edge id>` for each wall.
- **Tracking:** `brepjs` then carries the names through booleans using each
  operation's evolution record (`afterOperation`).
- **Derived faces:** the `origin` of a derived-face reference is the feature
  that named the two faces the round bridges, not a new name for the round.
- **Rule for the evaluator:** accept only `confidence: "exact"` for named faces.
  A `geometric-fallback` match can land on a different face, so it has to be
  shown as a broken reference that needs a re-pick. Derived faces
  (fillet/chamfer rounds) only ever resolve geometrically, because OCCT's
  fillet evolution is empty. For those, the fallback is the intended path.
- **Still open:** boolean seams and faces generated by booleans get no stable
  names. `brepjs` documents this as "history-fidelity work tracked separately".
  Sketch-on-face on such a face will need a role derived from its neighbours,
  the way derived faces work.

## Sketch solver (D3): planegcs

| Candidate                               | Verdict                                                                                                                                      |
| --------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------- |
| `brepjs` `ConstraintSketchCapability`   | Not usable: the occt-wasm adapter does not implement it (`supportsConstraintSketch` is false). It belongs to the alternative brepkit kernel. |
| planegcs (`@salusoft89/planegcs` 1.2.0) | Adopted.                                                                                                                                     |

planegcs is FreeCAD's solver compiled to WASM: a 0.5 MB WASM file, licensed
LGPL-2.0-or-later and shipped as a separate, replaceable file (see
`THIRD_PARTY_NOTICES.md`). `tests/sketch-solver.test.ts` confirms that it:

- **Solves from variables:** it solves a rectangle whose dimensions are sketch
  parameters, which are how the document's variables will enter.
- **Re-solves on change:** changing a parameter moves the geometry on the next
  solve.
- **Reports freedom:** `dof()` reports freedom that is left, for example 1 when
  the y anchor is missing.
- **Names conflicts:** it names a contradicting dimension in
  `get_gcs_conflicting_constraints()`.
- **Is fast:** re-solving a sketch of 20 rectangles (160 primitives) takes a
  median of 0.28 ms, against a 16 ms budget.

Notes for implementation:

- Set `debug_mode = DebugMode.NoDebug`, otherwise the solver prints to stdout.
- Destroy a solver's WASM module with `destroy_gcs_module()` when its sketch
  closes.
- Map sketch entities and constraints one to one onto planegcs primitive ids,
  so reported conflicts point straight at the offending constraint.

## UI shell (D6): Vite + React, with imperative three.js

`app/` is a Vite + React 19 shell next to the existing Studio. It exercises
every new piece together:

- it lists, creates and opens projects stored through `/api/projects`
- it edits a document's variables and rebuilds the model in the kernel worker
  as you type
- it shows the model in a three.js viewport
- it saves with revision checking: a save that lost a race reports the
  conflict instead of overwriting.

It works at desktop size and at 375 px on a phone.

Development and serving:

- `npm run app:dev` serves the shell from Vite with hot reload. It forwards
  the API, the kernel worker and the WASM to the CodeCAD server started with
  `npm run dev`.
- `npm run app:build` builds the shell into `app/dist`, which the CodeCAD
  server then serves at `/app/`.
- The shell is 780 KB, or 208 KB gzipped, most of it three.js. The kernel
  worker and WASM load separately.

Verdict: adopt it. Components suit the panels the editor needs (feature tree,
property panes, variable table, dialogs), and the builds are fast (about
0.1–0.3 s). The spike surfaced three rules for the real editor:

- **Long-lived resources live outside React state.** In development, React
  runs effects twice. A kernel worker created in `useMemo` and terminated in
  an effect's cleanup was reused after it had been stopped, and every build
  waited forever. The kernel is now a page-wide singleton, and
  `KernelClient.terminate()` makes waiting requests fail instead of hang.
- **The canvas is sized by a wrapper.** Sized directly by the layout, the
  canvas's drawing buffer fed back into the grid and grew until it squeezed
  the other panes (seen at phone width).
- **Measure before framing.** Camera fitting reads the canvas size at the
  moment it frames the model. A resize observer may not have run yet, and a
  portrait phone then shows the model cropped.

Next: move the Studio's viewer features (measurement, isolation, surface
visibility, the sheet editor) into this shell piece by piece. The code-first
Studio stays available until the new editor covers its features.
